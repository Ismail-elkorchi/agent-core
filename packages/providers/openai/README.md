# `@agent-core/provider-openai`

OpenAI Platform Responses API adapter for the provider-neutral contracts in `@agent-core/model`.

The default is `gpt-5.6-sol`. Trusted built-ins cover GPT-6 Astra, GPT-6.1 Sol, GPT-6 Sol, GPT-6 Luna, and the `gpt-5.6` Sol alias, Sol, Terra, Luna, GPT-5.5, and GPT-5.5 Pro; unknown models require a complete `OpenAIModelProfileDefinition`. Explicit definitions replace built-ins and are runtime-validated—partial profile merging is intentionally unsupported. GPT-5.6 profiles declare 1,050,000 context tokens, 922,000 maximum input tokens, 128,000 output tokens, efforts `low` through `max`, independent `standard|pro` modes, tiered component pricing, and the official `reasoning.mode` wire field. Current service tiers are `auto|default|flex|priority`; undocumented values fail before a request is sent.

Ordinary Platform requests are stateless: the adapter sends the full logical input with `store:false` and does not use `previous_response_id`. Bounded SSE/JSON framing is shared with the Codex adapter through `@agent-core/provider-openai-responses`, while authentication and product semantics remain separate.

## Typed protocol and modern execution

`compileRequest`, `completeCompiled` and `streamCompiled` bind accounting to an immutable provider body. Session variants retain transport state. An explicit request cap or compilation output reservation is sent as `max_output_tokens` when supported. The adapter does not choose an output allowance. System/developer/user roles stay in causal input order. Required Responses reasoning blocks become exact provider context state; they are never rebuilt from `raw` or display summaries.

At `https://api.openai.com/v1`, the verified GPT-6 profiles declare async direct function/custom tools and appended reasoning configuration. `transport: 'websocket'` enables native sessions; HTTP uses next-request delivery. Start governed native work with `session.streamCompiled(compiled, { signal, native: { admit } })`. `admit(dispatch)` must durably reserve and authorize the exact `dispatch.compiled` before returning. Missing admission rejects successor writes. Steering reserves bounded inherited parent output before its causative write; `generationDeliveryId` lets a subsequent required-result frame extend that same generation's reservation.

`continueNative({deliveryId,responseId,input,tools?})` starts independent activity at a completed response boundary while older async jobs remain pending. `deliverToolResults({deliveryId,responseId,results,sourceCalls})` needs no steering prerequisite. Each source binding retains its original `{responseId,catalogIdentity,toolCallId}`, even when the delivery parent or advertised catalog changes. Synchronous dependencies must all be supplied before continuation. New configuration and catalogs are compiled and accounted with the exact transport frame and retained context. Native steering accepts user contributions only.

`response_started` and `response_boundary` include `native` metadata: admitted input identity, generation/delivery IDs, the exact causal request/catalog, and structured pending/required call obligations. Runtime consumes each response boundary once for output, tools, and usage. The final `done` response is an **ordinary-consumer aggregate** of output, calls, and usage. A usage total or optional component is known only when every constituent response reports it. For runtime, `done` only closes the stream; it must never execute old calls or charge usage again.

Result delivery returns explicit submitted/acknowledged/applied/failed/uncertain states. `toolResultStatus`, `steeringStatus`, and `nativeDeliveryStatus` inspect retained evidence without sending. A uniquely correlated `response.created` proves application; it does not prove that successor inference completed or that a tool effect settled. Repeated identical delivery IDs query the same operation; changed input or reusing a call under another delivery rejects. Disconnects and uncertain sends are never retried. Transport closure prevents further writes immediately. The receive loop processes buffered provider evidence before classifying unresolved delivery: a received terminal response or confirmed application remains known after a disconnect. No server polling or restart recovery capability is claimed: hosts persist delivery records, retain saved tool results, and suspend uncertain delivery when application cannot be proven.


Verified model and protocol sources (2026-10-10): [GPT-6 guide](https://developers.openai.com/api/docs/guides/latest-model), [Sol 6.1](https://developers.openai.com/api/docs/models/gpt-6.1-sol), [Sol](https://developers.openai.com/api/docs/models/gpt-6-sol), [Luna](https://developers.openai.com/api/docs/models/gpt-6-luna), [Astra model](https://developers.openai.com/api/docs/models/gpt-6-astra), [async tools](https://developers.openai.com/api/docs/guides/async-tool-calling), [steering](https://developers.openai.com/api/docs/guides/steering). Deterministic fixtures validate framing; no live account/model availability or quality measurement is claimed.

`countTokens: true` resolves opaque/media input cost through the bounded, cancellable `/responses/input_tokens` endpoint; `maxConcurrentCounts` defaults to two. The exact compiled input/tools/schema are counted before invocation, without a second generation call. Hosts include this admission I/O in their resource policy. Source: [input token counts](https://developers.openai.com/api/reference/cli/resources/responses/subresources/input_tokens/methods/count). Public Platform requests explicitly request encrypted reasoning output for stateless replay; the Codex subscription adapter retains its endpoint-specific default behavior.

The protocol declares `contextReset: "fresh_request"`: after outstanding native responses and tool obligations settle, Core may create a fresh request from explicit sources. Ordinary reasoning and tool continuation remain exact within a request window. Fresh windows never call a provider compaction endpoint or replay a provider summary.
